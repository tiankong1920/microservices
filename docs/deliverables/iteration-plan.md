## 1. 版本管理策略

### 1.1 语义化版本（Semantic Versioning）

采用 `MAJOR.MINOR.PATCH` 三段式版本号，遵循 [SemVer 2.0](https://semver.org/) 规范：

| 段位 | 含义 | 递增条件 | 示例 |
|------|------|----------|------|
| **MAJOR** | 主版本 | 不兼容的 API 变更、架构升级、重大功能重构 | 3 → 4 |
| **MINOR** | 次版本 | 向后兼容的功能新增、模块扩展 | 3.0 → 3.1 |
| **PATCH** | 修订版本 | 向后兼容的缺陷修复、安全补丁 | 3.1.0 → 3.1.1 |

**附加规则**：

- 预发布版本追加后缀：`-alpha.1`、`-beta.2`、`-rc.1`（如 `v3.1.0-rc.1`）
- 构建元数据追加后缀：`+build.20260701`（如 `v3.1.0+build.20260701`）
- 正式发布版本**不得**携带预发布后缀

### 1.2 分支策略

采用 Git Flow 变体，适配微服务架构下的多仓库场景：

```
main ────────────────────────────────────────── 永远可部署
  │
  ├── release/3.1 ──────── 发布冻结分支
  │     │
  │     └── hotfix/3.1.1 ── 紧急修复
  │
  ├── develop ───────────── 开发集成分支
  │     │
  │     ├── feature/inventory-optimization ── 功能分支
  │     ├── feature/jacoco-coverage ───────── 功能分支
  │     └── feature/i18n-support ──────────── 功能分支
  │
  └── hotfix/3.0.1 ─────── 主线热修复
```

| 分支类型 | 命名规范 | 生命周期 | 合并目标 | 说明 |
|----------|----------|----------|----------|------|
| `main` | `main` | 永久 | — | 生产就绪代码，仅接受 merge/rebase |
| `release/*` | `release/{MAJOR.MINOR}` | 有限（发布后保留30天） | `main` + `develop` | 发布冻结，仅允许缺陷修复 |
| `develop` | `develop` | 永久 | — | 开发集成分支，CI 必须绿灯 |
| `feature/*` | `feature/{kebab-case-name}` | 短期（≤2周） | `develop` | 单一功能或用户故事 |
| `hotfix/*` | `hotfix/{MAJOR.MINOR.PATCH}` | 短期（≤24h） | `main` + `develop` | 生产环境紧急修复 |

**分支保护规则**：

- `main`：禁止直接推送，必须通过 PR + 至少 1 人 Code Review + CI 通过
- `develop`：禁止直接推送，必须通过 PR + CI 通过
- `release/*`：仅允许 cherry-pick 或限定范围的缺陷修复提交

### 1.3 标签与发布命名规范

| 类型 | 格式 | 示例 | 说明 |
|------|------|------|------|
| 正式发布 | `v{MAJOR.MINOR.PATCH}` | `v3.1.0` | 生产部署版本 |
| 预发布 | `v{MAJOR.MINOR.PATCH}-{stage}.{N}` | `v3.1.0-rc.2` | RC/Beta/Alpha |
| 热修复 | `v{MAJOR.MINOR.PATCH}` | `v3.0.1` | PATCH 版本递增 |
| 构建标签 | `build/{yyyy-MM-dd}.{N}` | `build/2026-07-01.3` | 当日第 N 次构建 |

**发布制品命名**：

- Docker 镜像：`jxcms/{service-name}:{version}`（如 `jxcms/inventory-service:3.1.0`）
- Helm Chart：`jxcms-helm-{version}.tgz`
- 发布说明：`CHANGELOG-{version}.md`

## 2. 迭代节奏

### 2.1 Sprint 周期

| 参数 | 规格 |
|------|------|
| Sprint 长度 | 2 周（10 个工作日） |
| 计划会议 | Sprint 第1天，2h |
| 每日站会 | 每日 15min，同步阻塞与进展 |
| 评审会议 | Sprint 最后1天，1.5h |
| 回顾会议 | Sprint 最后1天，1h |
| Sprint 容量 | 按 8 人·天/开发者 计算，预留 20% 缓冲 |

**Sprint 交付标准**：

- 所有承诺 Story 达到 **Done** 定义（代码合并 → 单测通过 → 代码审查 → 文档更新）
- `develop` 分支 CI 全绿
- Sprint Review 可演示

### 2.2 季度 Release 版本

| 节点 | 时间 | 版本 | 说明 |
|------|------|------|------|
| Q1 Release | 1-3月 | MINOR 版本 | 功能迭代 + 技术债清理 |
| Q2 Release | 4-6月 | MINOR 版本 | 功能迭代 + 安全加固 |
| Q3 Release | 7-9月 | MINOR/PATCH 版本 | 功能迭代 + 质量提升 |
| Q4 Release | 10-12月 | MAJOR/MINOR 版本 | 架构演进 + 重大功能 |

**Release 时间线**：

```
Q3 Release 示例（v3.1）：
├─ Week 1-2 : Sprint 1 — 规划 + 核心修复
├─ Week 3-4 : Sprint 2 — 修复 + 覆盖率
├─ Week 5-6 : Sprint 3 — 覆盖率 + 质量门
├─ Week 7   : Code Freeze + RC 测试
├─ Week 8   : UAT + 修复 + 正式发布
└─ Week 9-10: 上线监控 + 复盘
```

### 2.3 热修复流程（24h 响应）

```
生产缺陷报告（P0/P1）
    │
    ▼
┌──────────────────────┐
│  0-1h：问题确认与定级  │  ← 值班工程师
│  1-4h：分支创建与修复  │  ← hotfix/* 分支
│  4-8h：Code Review    │  ← 紧急通道，1人审批
│  8-12h：CI + 冒烟测试  │  ← 限定测试范围
│  12-18h：灰度部署      │  ← 5% → 25% → 100%
│  18-24h：全量发布 + 监控│  ← 同步 develop
└──────────────────────┘
```

**热修复分级**：

| 级别 | 定义 | 响应时间 | 修复窗口 |
|------|------|----------|----------|
| P0-紧急 | 服务不可用 / 数据丢失风险 | ≤15min | ≤4h |
| P1-高 | 核心功能受损 / 安全漏洞 | ≤1h | ≤8h |
| P2-中 | 非核心功能异常 | ≤4h | ≤24h（走正常迭代） |

## 7. 变更管理流程

### 7.1 RFC（Request for Change）流程

```
变更发起 → RFC 文档 → 影响分析 → 变更评审 → 批准/拒绝 → 实施 → 验证 → 关闭
```

**RFC 文档模板**：

| 字段 | 说明 |
|------|------|
| RFC 编号 | `RFC-{yyyy}-{NNN}`（如 RFC-2026-001） |
| 发起人 | 变更发起者 |
| 变更类型 | 功能变更 / 架构变更 / 配置变更 / 安全变更 |
| 变更描述 | 变更内容与原因 |
| 影响范围 | 受影响模块、服务、接口 |
| 风险等级 | 高 / 中 / 低 |
| 回滚方案 | 变更失败时的回滚步骤 |
| 实施计划 | 时间窗口、步骤、验证方法 |
| 审批人 | 变更评审委员会成员 |

### 7.2 变更评审委员会（Change Advisory Board, CAB）

| 角色 | 人员 | 职责 |
|------|------|------|
| CAB 主席 | 技术负责人 | 最终审批权 |
| 产品代表 | 产品经理 | 业务影响评估 |
| 架构代表 | 架构师 | 技术影响评估 |
| 运维代表 | DevOps 工程师 | 部署与运维影响评估 |
| QA 代表 | 测试负责人 | 质量与测试影响评估 |

**审批权限**：

| 变更类型 | 审批层级 | 审批时限 |
|----------|----------|----------|
| P0 紧急变更 | CAB 主席单人审批 | ≤1h |
| 架构变更 | CAB 全员评审 | ≤2 个工作日 |
| 功能变更 | 产品 + 架构代表 | ≤1 个工作日 |
| 配置变更 | 运维代表 | ≤4h |

### 7.3 影响分析与回滚方案

**影响分析检查项**：

- [ ] 受影响微服务清单（直接 + 间接依赖）
- [ ] API 契约变更（是否向后兼容）
- [ ] 数据库 Schema 变更（是否需要迁移脚本）
- [ ] 配置项变更（是否需要灰度配置）
- [ ] 第三方依赖变更（版本升级风险评估）
- [ ] 性能影响（是否需要压测验证）

**回滚方案要求**：

| 场景 | 回滚策略 | RTO |
|------|----------|-----|
| 微服务部署异常 | 回滚至上一版本镜像 | ≤10min |
| 数据库 Schema 不兼容 | 执行逆向迁移脚本 | ≤30min |
| 配置变更导致异常 | 配置中心回滚至上一版本 | ≤5min |
| 全量发布失败 | Blue-Green 切换回旧环境 | ≤15min |
