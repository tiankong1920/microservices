# 采购到收货完整业务流程

## 流程概述

本文档描述了从创建采购订单到确认收货的完整业务流程，涵盖了采购管理和进货管理两个核心模块的交互。

## 业务流程步骤

### 1. 创建采购订单

用户首先在系统中创建采购订单，包含供应商信息和采购商品明细。

**API端点**: `POST /api/v1/purchase-orders`

**请求示例**:
```json
{
  "supplierId": "SUP001",
  "orderNumber": "PO20230001",
  "orderDate": "2023-01-01T00:00:00",
  "remarks": "测试采购订单",
  "items": [
    {
      "productId": "P001",
      "quantity": 100,
      "unitPrice": 10.00
    },
    {
      "productId": "P002",
      "quantity": 50,
      "unitPrice": 20.00
    }
  ]
}
```

### 2. 审批采购订单

采购订单创建后，需要经过审批流程，将状态从"pending"更新为"confirmed"。

**API端点**: `PUT /api/v1/purchase-orders/{id}`

### 3. 创建进货订单

采购订单审批通过后，根据采购订单创建进货订单。

**API端点**: `POST /api/v1/receiving-orders/from-purchase-order/{purchaseOrderId}`

### 4. 确认收货

货物到达后，进行收货确认操作，系统会自动更新库存。

**API端点**: `POST /api/v1/receiving-orders/receive`

**请求示例**:
```json
{
  "receivingOrderId": 1,
  "items": [
    {
      "itemId": 1,
      "receivedQuantity": 100,
      "rejectedQuantity": 0
    },
    {
      "itemId": 2,
      "receivedQuantity": 50,
      "rejectedQuantity": 0
    }
  ]
}
```

## 状态流转

### 采购订单状态
1. **pending**: 待处理
2. **confirmed**: 已确认
3. **completed**: 已完成
4. **cancelled**: 已取消

### 进货订单状态
1. **PENDING**: 待处理
2. **CONFIRMED**: 已确认
3. **PROCESSING**: 处理中
4. **PARTIALLY_RECEIVED**: 部分收货
5. **RECEIVED**: 已收货
6. **COMPLETED**: 已完成
7. **CANCELLED**: 已取消

### 收货状态
1. **NOT_RECEIVED**: 未收货
2. **PARTIALLY_RECEIVED**: 部分收货
3. **FULLY_RECEIVED**: 全部收货

## 异常处理

### 1. 重复订单号
- **场景**: 创建采购订单时使用已存在的订单号
- **处理**: 系统返回错误码30002，提示订单号已存在

### 2. 版本冲突
- **场景**: 更新采购订单时版本号不匹配
- **处理**: 系统返回错误码30003，提示版本冲突

### 3. 订单不存在
- **场景**: 操作不存在的采购订单或进货订单
- **处理**: 系统返回错误码30001，提示订单不存在

### 4. 收货数量超限
- **场景**: 实际收货数量超过订购数量
- **处理**: 系统抛出运行时异常，提示收货数量超出限制

## 数据一致性保证

### 事务管理
- 采购订单创建和明细保存在同一事务中
- 进货订单创建和明细保存在同一事务中
- 收货确认操作使用事务保证数据一致性

### 并发控制
- 采购订单使用版本号机制防止并发更新
- 进货订单通过状态检查防止非法操作

## 集成点

### 1. 与库存服务集成
- 确认收货时通过Feign客户端调用库存服务更新库存
- 库存更新失败时记录日志但不中断主流程

### 2. 与订单服务集成
- 进货订单服务通过Feign客户端获取采购订单信息
- 保证数据一致性

## 事件发布

### 1. 进货订单创建事件
- 发布时机: 进货订单创建完成
- 用途: 通知其他服务进货订单已创建

### 2. 收货完成事件
- 发布时机: 确认收货完成
- 用途: 通知其他服务收货已完成，触发后续业务流程

## 性能优化

### 1. 批量操作
- 收货确认支持批量处理多个商品

### 2. 缓存机制
- 采购订单信息在进货订单创建时缓存
- 减少服务间调用次数

## 安全考虑

### 1. 数据验证
- 所有输入参数进行验证
- 防止SQL注入和XSS攻击

### 2. 权限控制
- 不同角色具有不同的操作权限
- 敏感操作需要相应权限

## 监控和日志

### 1. 关键操作日志
- 采购订单创建/更新/删除
- 进货订单创建/更新
- 收货确认操作

### 2. 异常日志
- 记录所有异常情况
- 便于问题排查和系统优化
